AWS Cloud Infrastructure

A three-tier web application environment built on AWS with Terraform, private EC2 workloads, managed MySQL, and automated container deployments through GitHub Actions.

I built this project to understand how networking, security, infrastructure provisioning, and application delivery work together across a complete AWS environment.

overview

This project implements a complete three-tier application environment on AWS, hosting a Vue frontend and a Flask API backed by MySQL.

Public traffic enters through an internet-facing Application Load Balancer, while the web, application, and database tiers run in isolated subnet groups. Terraform provisions the infrastructure, Docker packages the applications, and GitHub Actions handles testing, image publishing, database migrations, and rolling deployments.

The environment is intentionally disposable. It can be created for demonstration, validated through a complete request and deployment lifecycle, and destroyed afterward to keep the running cost practical for a portfolio project.

architecture

A request passes through four clearly separated layers:

  1. 1. Public entry point

    Cloudflare resolves the application domain to an internet-facing AWS Application Load Balancer. The load balancer redirects HTTP traffic to HTTPS and terminates TLS using an ACM certificate.

  2. 2. Web tier

    The public load balancer forwards requests to Nginx instances running in an EC2 Auto Scaling Group across private web subnets. Nginx serves the Vue frontend and proxies API requests to an internal endpoint.

  3. 3. Application tier

    API traffic passes through an internal Application Load Balancer to Flask and Gunicorn containers running on EC2 instances in private application subnets. This tier contains the application logic and cannot be accessed directly from the internet.

  4. 4. Data tier

    The backend connects to an encrypted RDS MySQL instance located in isolated database subnets. Only the application tier can reach the database port, and the database has neither a public endpoint nor an internet route.

This separation creates explicit trust boundaries and allows each tier to be secured, scaled, deployed, and diagnosed independently.

features

01

Modular Infrastructure as Code

The infrastructure is divided into reusable Terraform modules for networking, security groups, load balancers, compute, RDS, DNS, and CI/CD IAM.

I chose this structure to keep responsibilities explicit and make changes easier to review. The result is a codebase where individual infrastructure concerns can evolve without turning the entire environment into one tightly coupled configuration.

02

Private Compute Tiers

Both web and application EC2 instances run in private subnets. Only the public load balancer is internet-facing.

I made this choice to reduce the public attack surface. Users can reach the application, but they cannot connect directly to its instances or database.

03

Separate Public and Internal Load Balancers

The public ALB handles browser traffic, while the internal ALB exposes the API only to the web tier.

Although a single load balancer would cost less, using two made the public/private boundary explicit and demonstrated independent routing and health checking for each application tier.

04

OIDC Authentication for GitHub Actions

GitHub Actions accesses AWS through OpenID Connect instead of stored AWS access keys.

Separate IAM roles are used for Terraform planning, infrastructure changes, and application deployment. This limits the impact of each workflow and removes the need to rotate long-lived CI credentials.

05

Runtime Configuration Through AWS Systems Manager

Application image versions and non-secret database metadata are stored in SSM Parameter Store. Instances retrieve their configuration during startup.

This separates infrastructure definition from application release state. A new application version can be deployed without changing or reapplying the Terraform configuration.

06

Auto Scaling and Health-Based Replacement

The web and application tiers use Launch Templates and Auto Scaling Groups connected to ALB health checks.

This provides consistent instance creation and allows unhealthy or outdated instances to be replaced automatically. It also made immutable deployments possible through controlled Instance Refresh operations.

security_model

Network Isolation

The VPC is divided into public, web, application, and database subnet groups. Web and application instances have no public IP-based entry path, while database subnets have no NAT route.

Only the public ALB is directly reachable from the internet.

Explicit Tier-to-Tier Access

Security groups reference other security groups instead of broad network ranges:

  • Internet → public ALB on ports 80 and 443
  • Public ALB → web tier on the web service port
  • Web tier → internal ALB on port 80
  • Internal ALB → application tier on the backend port
  • Application tier → RDS on the MySQL port

This means network access is granted according to workload identity and responsibility rather than only subnet location.

TLS Boundary

Public HTTP requests are redirected to HTTPS, and TLS is terminated at the public ALB using an ACM certificate and a modern TLS policy.

Traffic behind the public ALB uses HTTP inside private subnets. This is a documented cost-and-complexity trade-off rather than an assumption that all internal traffic is automatically trusted.

Secrets Management

The database password remains in the AWS-managed RDS master secret. The backend instance role can retrieve only the required database metadata and secret at runtime.

This prevents sensitive credentials from being embedded in images, source code, EC2 user data, or application deployment jobs.

Administrative Access

The instances are managed through AWS Systems Manager rather than public SSH access. No inbound SSH rule is required, and administrators do not need to manage bastion hosts or distribute private SSH keys.

CI/CD Permissions

GitHub Actions uses short-lived OIDC sessions. Terraform plan, Terraform apply, and application deployment use separate IAM roles, while GitHub Environments can add branch restrictions or reviewer approval to sensitive operations.

estimated_costs

I used Cloudcraft to model the estimated monthly operating cost of the development environment in eu-central-1. The model reflects the main resources in the current architecture, including four burstable EC2 instances, two Application Load Balancers, two NAT gateways, an ECR repository, and a Multi-AZ RDS MySQL database.

Based on these assumptions, the environment is estimated at approximately $192.40 per month. Networking represents the largest share of the projected cost, particularly the NAT gateways and load balancers. This reinforces why the environment is designed to be temporary and why replacing some NAT traffic with VPC endpoints is an important future optimization.

This figure is a directional estimate rather than a billing guarantee. Actual cost will vary with runtime, traffic, data transfer, storage, backups, CloudWatch ingestion, AWS pricing changes, and any services not represented in the model.

tradeoffs

Disposable Database Defaults

RDS deletion protection and final snapshots are disabled by default so the complete demo can be destroyed without retaining chargeable resources.

A production environment should enable deletion protection, retain final snapshots, increase backup retention, and regularly test database restoration.

NAT Gateways Instead of VPC Endpoints

Private instances access ECR, SSM, and CloudWatch through NAT gateways. This reduced initial networking complexity but created a significant recurring cost.

A long-lived environment should evaluate VPC endpoints for SSM, ECR, CloudWatch Logs, and S3.

Reduced Observability

ALB access logs, VPC Flow Logs, and advanced database observability are not enabled by default.

This keeps a temporary environment cheaper, but a production system would require centralized logs, longer retention, alarms, dashboards, and an incident investigation strategy.

External Prerequisites

The ACM certificate, ECR repository, GitHub OIDC provider, and some CloudWatch configuration must exist before deployment.

This keeps the main stack focused, but means the environment is not yet fully reproducible through one command.

Next improvements

Add AWS Private Endpoints

Introduce configurable VPC endpoints for SSM, ECR, CloudWatch Logs, and S3 to reduce NAT dependency and keep AWS service traffic on the AWS network.

Automate All Runtime Prerequisites

Manage or bootstrap the remaining CloudWatch agent parameters and other setup dependencies consistently, removing manual steps from first deployment.

Introduce Production Profiles

Add environment-specific configurations for development, staging, and production, with production-safe defaults for deletion protection, backups, log retention, scaling, and approval gates.

Strengthen Observability

Enable VPC Flow Logs and ALB access logs, then add CloudWatch dashboards and alarms for unhealthy targets, failed instance refreshes, database capacity, latency, and application errors.

lessons

Private Instances Still Need Outbound Dependencies

Moving EC2 instances into private subnets does not remove their need to contact ECR, SSM, CloudWatch, and other AWS APIs.

Designing their outbound path made the relationship between private networking, NAT gateways, VPC endpoints, IAM permissions, and instance bootstrapping much clearer.

Infrastructure State Has a Different Lifecycle

If the state bucket were managed by the same stack as the application, destroying the demo could also remove the information required to manage it safely.

Bootstrapping the backend separately taught me to separate control-plane resources from short-lived workload resources.

CI/CD Identity Should Match the Operation

A pipeline that can plan infrastructure does not need the permissions required to apply it, and an application deployment should not have unrestricted infrastructure access.

Creating separate OIDC roles made least privilege concrete and easier to reason about than one shared automation role.

Health Checks Are Part of Deployment Logic

Starting an instance is not the same as successfully deploying an application. The rollout is complete only after new instances start their containers, pass target-group health checks, and replace the previous capacity.
