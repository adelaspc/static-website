overview

This project implements a three-tier application environment on AWS, hosting a Vue frontend and a Flask API backed by MySQL.

Cloudflare directs public traffic to an internet-facing Application Load Balancer. Nginx and Flask/Gunicorn run on separate private EC2 tiers, with an internal load balancer between them and RDS MySQL in isolated database subnets. Terraform provisions the infrastructure, while Docker and GitHub Actions deliver the application.

The environment is intentionally disposable: it can be provisioned for demonstration, validated through a complete request and deployment lifecycle, and destroyed afterward to control portfolio costs.

architecture

A request follows one explicit path through the environment.

Cloudflare → public ALB → Nginx → internal ALB → Flask/Gunicorn → RDS MySQL

  1. 01

    Public entry point

    Cloudflare resolves the application domain to the public ALB, which redirects HTTP to HTTPS and terminates TLS with ACM.

  2. 02

    Web tier

    The public ALB forwards traffic to Nginx containers in a private EC2 Auto Scaling Group. Nginx serves Vue and proxies API requests.

  3. 03

    Application tier

    The internal ALB routes API traffic to Flask/Gunicorn containers in a separate private EC2 Auto Scaling Group.

  4. 04

    Data tier

    The application connects to encrypted RDS MySQL in isolated database subnets; the database has no public endpoint or internet route.

key_engineering_decisions

The choices that define the implementation and its boundaries.

Private compute tiers

Web and application instances have no direct public entry path.

Why it matters: Incoming requests must pass through the load-balancing boundaries instead of reaching EC2 directly.

Separate load balancers

A public ALB handles browser traffic while an internal ALB exposes the API only to the web tier.

Why it matters: The public/private boundary, routing and health checks remain explicit for each application tier.

Modular Terraform

Networking, security groups, load balancers, compute, RDS, DNS and CI/CD IAM have separate responsibilities.

Why it matters: Infrastructure concerns can be reviewed and changed without one tightly coupled configuration.

Keyless CI/CD authentication

GitHub Actions assumes AWS roles through OIDC instead of using stored access keys.

Why it matters: Short-lived sessions and operation-specific roles reduce the reach of each workflow.

Runtime configuration

Image versions and non-secret database metadata are stored in SSM Parameter Store; the RDS password remains in its AWS-managed secret.

Why it matters: Release state and credentials stay out of application images and Terraform variables.

Image-based replacement

Auto Scaling Instance Refresh replaces instances with containers built from immutable image tags.

Why it matters: New instances retrieve the intended release configuration during startup and must pass load-balancer health checks.

deployment_flow

Application delivery is separate from Terraform infrastructure changes. GitHub Actions uses OIDC for AWS access; Terraform apply and application deployment have distinct roles and approval gates.

  1. 01

    Validate

    Test the Flask backend and build the Vue frontend.

  2. 02

    Build

    Build immutable backend and frontend Docker images tagged with the Git commit SHA.

  3. 03

    Publish

    Push both application images to Amazon ECR.

  4. 04

    Migrate

    Run the database migration before the new image tags become active.

  5. 05

    Refresh

    Update SSM image parameters, then refresh the application tier before the web tier.

Technical release details
  • • Replacement instances retrieve their image tags from SSM Parameter Store during startup.
  • • The workflow waits for each Instance Refresh to complete and for replacement capacity to pass target-group health checks.
  • • Infrastructure deployment remains a separate Terraform workflow; apply is manually gated.
  • • The current flow does not claim automatic rollback.

Administrative access

Instances are managed through AWS Systems Manager. There is no public SSH path or inbound SSH rule.

Database credentials

The password remains in the AWS-managed RDS master secret; the backend role retrieves only the required metadata and secret at runtime.

CI/CD identity

GitHub Actions uses short-lived OIDC sessions and separate IAM roles for planning, infrastructure changes and application deployment.

TLS boundary

TLS terminates at the public ALB. Traffic behind it currently uses HTTP inside private subnets; end-to-end TLS is not claimed.

tradeoffs

Disposable database defaults

Deletion protection and final snapshots are disabled so the demo can be destroyed without retaining chargeable resources.

For a longer-lived environment: enable deletion protection, retain final snapshots, increase backup retention and test restoration.

NAT gateways over VPC endpoints

NAT gateways keep initial networking simpler while private instances reach ECR, SSM and CloudWatch, but create recurring cost.

For a longer-lived environment: evaluate endpoints for SSM, ECR, CloudWatch Logs and S3.

Reduced observability

ALB access logs, VPC Flow Logs and advanced database observability are not enabled by default to keep a temporary environment cheaper.

For a longer-lived environment: centralize logs and add retention, alarms, dashboards and an investigation strategy.

Internal HTTP

TLS terminates at the public ALB; traffic behind it uses HTTP within private subnets as an explicit cost-and-complexity decision.

For a production-oriented environment: reassess the internal encryption boundary rather than treating private networking as automatic trust.

Additional implementation constraint

The ACM certificate, ECR repository, GitHub OIDC provider and some CloudWatch configuration must exist before deployment. Keeping them outside the main stack narrows its focus, but means the environment is not yet reproducible through one command.

lessons_learned

Private does not mean disconnected

I learned to design outbound access for ECR, SSM, CloudWatch and other AWS APIs alongside routing, IAM and instance bootstrapping.

Infrastructure state has a different lifecycle

Bootstrapping the backend separately clarified why control-plane resources should outlive short-lived workload resources.

CI/CD identity should match the operation

Separate OIDC roles made least privilege more concrete than one shared automation role with planning, apply and deployment access.

Health checks are deployment logic

Starting an instance is not a completed rollout; replacement capacity must start its containers and pass target-group health checks.

next_improvements

Add configurable VPC endpoints

Reduce NAT dependency for SSM, ECR, CloudWatch Logs and S3 while keeping AWS service traffic on the AWS network.

Strengthen observability

Enable VPC Flow Logs and ALB access logs, then add CloudWatch dashboards and alarms for the existing infrastructure and application signals.

Introduce environment profiles

Add development, staging and production configurations with appropriate deletion protection, backups, retention, scaling and approval defaults.

Automate runtime prerequisites

Bootstrap the remaining CloudWatch agent parameters and setup dependencies consistently to remove manual first-deployment steps.
